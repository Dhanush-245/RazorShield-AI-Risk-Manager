# RAZORSHIELD AI — ADVANCED AI RISK MANAGER

## Complete Project Specification and Development Master Prompt

You are an expert AI/ML architect, fraud-risk engineer, data scientist, generative-AI engineer, agentic-AI engineer, backend engineer, and hackathon mentor.

Help me build a production-oriented, advanced AI Risk Manager called **RazorShield AI** for the Razorpay Buildathon **Track 02 — AI Risk Manager**.

The official problem is:

> **Stop the merchant losing money to fraud, returns and chargebacks.**

The official track requires:

> Build a working detector, verifier, or auto-responder for one class of loss, with measured precision and recall on a held-out test set.

The official example directions are:

1. Chargeback evidence responder
2. Return-risk scorer
3. Fraud-spike detector
4. Abuse-ring sentinel

The project must remain **strictly defense-only**. Do not build, recommend, or implement anything that enables fraud, payment abuse, evasion, exploitation, attack automation, or bypassing risk controls.

---

# 1. PROJECT VISION

Build RazorShield AI as an advanced merchant-risk intelligence system that helps merchants detect, investigate, explain, prioritize, and respond to financial risk.

The system should not be merely a fraud-classification model.

The complete concept is:

> **Detect → Investigate → Explain → Assess → Recommend → Human Approval → Act → Audit**

The primary measurable objective should be **fraud-related loss prevention**, while the other official Track 02 directions become supporting intelligence modules.

The project should demonstrate how multiple AI/ML techniques can work together as one coherent risk-management system.

---

# 2. CORE PROJECT IDEA

RazorShield AI receives transaction, customer, merchant, device, behavioral, return, and chargeback information.

It analyzes the information using multiple layers:

* Supervised fraud detection
* Unsupervised anomaly detection
* Behavioral analysis
* Transaction velocity analysis
* Risk rules
* Graph/entity relationship analysis
* Return-risk prediction
* Chargeback evidence analysis
* Explainable AI
* Evidence-grounded LLM investigation
* Risk fusion
* Bounded defensive AI agent
* Human-in-the-loop approval
* Audit logging

The final system should generate a transparent risk assessment.

Example:

Transaction:

TX_10982

Risk Score:

93/100

Fraud Probability:

0.94

Anomaly Score:

0.89

Abuse-Ring Score:

0.82

Decision:

HIGH RISK — MANUAL REVIEW

Reasons:

1. Transaction amount is significantly outside the customer's normal behavior.
2. A new device was detected.
3. Transaction velocity is unusually high.
4. The device is associated with multiple suspicious accounts.
5. Recent failed transactions increase the risk.

Recommended defensive action:

Temporarily hold the transaction and request additional verification.

The system must also preserve the evidence and decision in an audit trail.

# 3. IMPORTANT ARCHITECTURAL PRINCIPLE

Do NOT build four disconnected mini-projects.

Build ONE integrated AI Risk Manager.

The four official directions should have different roles:

### Primary measurable objective

**Fraud-Spike Detector**

This is the main fraud/loss detection task and should receive rigorous held-out evaluation.

### Supporting intelligence

**Abuse-Ring Sentinel**

Graph/network-based risk intelligence.

**Return-Risk Scorer**

Secondary merchant-loss prediction.

**Chargeback Evidence Responder**

Evidence retrieval, verification, summarization, and response generation.

The entire system should connect these components through a common risk engine.

# 46. DEVELOPMENT RULES

Follow these rules throughout the project:

1. Do not fabricate metrics.
2. Do not fabricate dataset information.
3. Do not claim real-world performance without evidence.
4. Keep the test set isolated.
5. Prevent data leakage.
6. Explain every major modeling decision.
7. Prefer simple models when they perform equally well.
8. Do not add technologies merely for buzzwords.
9. Every AI feature must have a clear purpose.
10. Every agent action must be bounded.
11. Keep the project strictly defensive.
12. Preserve an audit trail.
13. Clearly distinguish real and synthetic data.
14. Test failure cases.
15. Optimize for precision/recall and business impact rather than accuracy alone.
16. Keep the system reproducible.
17. Version datasets, models and prompts.
18. Never allow the LLM to invent evidence.
19. Never allow the agent to bypass risk controls.
20. Human approval must be available for high-impact actions.

# 50. DEFINITION OF DONE

RazorShield AI is complete only when:

* A real working fraud-risk model exists.
* It is evaluated on a held-out test set.
* Precision and recall are reported.
* False-positive cost is measured.
* Fraud-spike detection works.
* Anomaly detection works.
* Behavioral risk analysis works.
* Abuse-ring analysis works where data permits.
* Return-risk scoring works where data permits.
* Chargeback evidence generation works using verified evidence.
* AI investigation is evidence-grounded.
* Risk fusion produces an interpretable risk score.
* The agent can perform bounded defensive workflows.
* Human approval exists for sensitive decisions.
* All actions are logged.
* Failure analysis has been completed.
* Stress testing has been completed.
* The system has a working API.
* A usable dashboard exists.
* Documentation is complete.
* The system can be demonstrated end-to-end.
* No fabricated metrics or evidence are used.
* The entire system remains strictly defense-only.
