# RazorShield model pipeline

The bundled competition demo trains real scikit-learn estimators on a deterministic **synthetic**
merchant-risk dataset. Synthetic records are used because the complete entity, return, chargeback,
device, location and temporal schema is not available in one public dataset. The generated data and
its evaluation must not be represented as real-world model performance.

Run from the repository root:

```bash
backend/.venv/bin/python ml/training/train_models.py
```

The script uses earlier records for training and later records for held-out evaluation. Fusion
stacking also uses expanding temporal windows: every component prediction used to train fusion is
generated by models fitted only on earlier rows. It writes
versioned artifacts and an evaluation manifest to `ml/artifacts/`. Production inference only loads
those artifacts; it never trains inside an API request.

## Dataset responsibilities

Do not merge every learning task into one undifferentiated dataset:

- The supervised classifier needs transaction outcomes (`fraud` or `legitimate`).
- The anomaly detector fits only legitimate rows from the chronological training window.
- Behavioral and velocity features must be computed from events strictly before the transaction.
- Graph features come from customer-device-location-recipient relationships available at scoring time.
- The bundled synthetic data exists for pipeline and product demonstration. It is not evidence of
  production performance and must not replace authorized, merchant-specific training data.

The intended production flow is supervised fraud probability + unsupervised anomaly evidence +
versioned context rules, followed by a trained fusion probability, validation-selected LOW/MEDIUM/HIGH
thresholds, an explanation/evidence pack, and human investigation. No score is proof of fraud.

## Contextual risk model (v3)

Version 3 evaluates a transaction as a relationship between the customer, recipient, device,
location, amount and recent activity. Its 24 inputs include customer and account history,
recipient verification and prior use, customer-to-recipient history, same-recipient velocity,
recipient network breadth, device sharing, amount deviation and transaction intent.

Age is contextual information—not a fraud verdict. In particular, the engine never treats an
adult customer or a college payment as automatically safe. A high-value education payment only
receives a bounded risk reduction when the recipient is verified and previously used, the
customer-recipient relationship is established, velocity is low, and the device and location are
familiar. Conversely, an unknown or high-risk recipient combined with high value, novelty or a
burst of payments increases risk.

The API enriches missing history and recipient-network inputs from the active merchant dataset,
then automatically runs the fraud, anomaly, behavior, velocity, graph and contextual-rule
components. Their outputs are fused into one risk score and explanation for human review.

The current deterministic synthetic holdout results are recorded in `ml/artifacts/manifest.json`.
They include aggregate metrics and age-slice alert/false-positive rates so regressions can be
noticed during development. These values validate the demo pipeline only; deployment requires
merchant-specific labelled data, temporal backtesting, calibration and fairness monitoring.

## Real IEEE-CIS pipeline gate

The real-data workflow is deliberately separate from the bundled synthetic artifacts. It must not
read the 1,000-row RazorShield application-test CSV and it does not overwrite `ml/artifacts/`.
IEEE-CIS competition data is authorized only for the purposes stated in its Kaggle rules; it is a
non-commercial benchmark, not a deployable commercial training source. Model governance therefore
requires explicit commercial data authorization and fails closed when that evidence is absent.

After accepting the IEEE-CIS Fraud Detection competition rules in Kaggle, place only these files in
`ml/data/raw/`:

```text
ml/data/raw/train_transaction.csv
ml/data/raw/train_identity.csv
```

If the official Kaggle CLI is configured for your account, the download command is:

```bash
kaggle competitions download -c ieee-fraud-detection -p ml/data/raw
unzip ml/data/raw/ieee-fraud-detection.zip -d ml/data/raw
```

Run the mandatory audit before any training:

```bash
PYTHONPATH=. backend/.venv/bin/python -m ml.training.ieee_cis_audit
```

The command writes `ml/reports/ieee_cis/data_audit.json` and `data_audit.md` with exact row/column
counts, target balance, missingness, duplicate IDs, identity join coverage, timestamp bounds, and
leakage controls. It fails closed if either official file or any essential column is absent.

The local audit and v2 training have completed. Five candidate algorithms were
compared using a 70/7.5/7.5/15 train/calibration/selection/test split, selecting
XGBoost. The frozen 88,581-row test report reproduced on 2026-08-31. It remains
candidate-only and fails the requested production acceptance targets. Audit new
source inputs before any new training. See [the current real-data workflow](../docs/REAL_ML_PIPELINE.md)
and [metrics, costs and limitations](../docs/EVALUATION.md).
